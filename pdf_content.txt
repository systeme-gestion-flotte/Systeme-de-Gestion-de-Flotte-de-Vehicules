5 Bonnes pratiques à respecter
Architecture polyglotte
Choisissez le meilleur langage pour chaque service selon vos compétences et les besoins
spécifiques :
—Java/Spring Boot/Quarkus :Services critiques nécessitant robustesse et perfor-
mance
—Node.js/NestJS :Services I/O intensifs, temps réel, rapidité de développement
—Python/FastAPI/FastAPi :Data processing, ML, scripts d’automatisation
Sécurité centralisée
Principe du Zero Trust :
— Utilisez Keycloak comme point unique d’authentification
— Ne gérez JAMAIS les mots de passe directement dans les services
— Implémentez le principe du moindre privilège avec RBAC
— Stockez les secrets dans Kubernetes Secrets ou Vault
— Chiffrez les communications inter-services (mTLS)
Observabilité dès le départ
Les 3 piliers avec OpenTelemetry :
—Traces :Traçage distribué avec Jaeger (comprendre le flux des requêtes)
—Métriques :Prometheus (RED : Rate, Errors, Duration / USE : Utilization, Satura-
tion, Errors)
—Logs :Structured logging (JSON) avec correlation ID, agrégation avec Loki
— Ajoutez des métriques métier (véhicules actifs, alertes, etc.)
Déploiement automatisé
Pipeline CI/CD :
— Build automatique des images Docker
— Tests unitaires et d’intégration obligatoires
— Scan de sécurité des images (Trivy, Snyk)
— Déploiement automatique en environnement de dev
— Utilisation de Helm pour versionner les déploiements

8 FAQ - Questions fréquentes
Q : Peut-on utiliser un seul langage pour tous les services?
Oui, absolument! L’architecture polyglotte est une option, pas une obligation. Si toute
l’équipe maîtrise mieux un langage (par ex. Node.js), utilisez-le partout. L’important est
de livrer un projet fonctionnel.
Q : Faut-il déployer sur un vrai cluster Kubernetes?
Non. Utilisez Minikube, Kind, ou K3s en local. Docker Desktop inclut également Kuber-
netes. L’important est de démontrer la conteneurisation et l’orchestration.
Q : Comment gérer les données de test?
Créez des scripts de seed (migrations + fixtures) pour initialiser la base avec des don-
nées cohérentes. Utilisez Faker.js ou des bibliothèques similaires pour générer des données
réalistes.
Q : Que faire si on prend du retard sur le planning?
Priorisez!Concentrez-vous sur un MVP fonctionnel avec 2-3 services essentiels plutôt
que 5 services incomplets. Documentez les choix de priorisation dans un ADR.
Q : Doit-on implémenter tous les rôles RBAC?
Minimum : 2 rôles (admin et utilisateur). Les 4 rôles complets sont un plus, mais la sécurité
de base (authentification + 2 rôles) est suffisante.
Q : Comment répartir le travail en équipe?
Suggestion : 1 personne par service principal + rotations. Évitez les silos : faites du pair
programming et des revues de code croisées pour partager les connaissances.

9 Conseils pour réussir
9.1 Organisation d’équipe
—Travaillez en équipe :Répartissez les microservices entre les membres
—Daily standups :10-15 minutes chaque jour pour synchroniser
—Pair programming :Surtout pour les parties complexes (Kafka, K8s)
—Revues de code :Obligatoires avant tout merge en main
—Rétrospectives :Fin de chaque semaine, ajustez le cap
9.2 Gestion du code
—Git flow :Branches par feature, commits atomiques et descriptifs
—Conventional Commits :feat:,fix:,docs:, etc.
—Pull Requests :Description claire, tests passants, revue obligatoire
—Monorepo ou multi-repo :Les deux fonctionnent, choisissez selon vos préférences
9.3 Tests et qualité
—Tests d’abord :TDD quand possible, au minimum tests après chaque feature
—Couverture :Visez 70-80%, concentrez-vous sur la logique métier
—Tests d’intégration :Testez les interactions entre services
—Linting :ESLint, Prettier, etc. - configurez dès le début
9.4 Communication
—Slack/Discord :Canal dédié au projet, partage rapide
—Documentation :README à jour, ADR pour les décisions importantes
—Démos :Présentez vos avancées chaque semaine (même en interne)
—Questions :N’hésitez pas à demander de l’aide (profs, forums, communauté)
9.5 Ressources d’apprentissage
—Documentation officielle :Toujours la meilleure source
—Stack Overflow :Pour les problèmes techniques précis
—GitHub :Inspirez-vous de projets similaires (avec attribution!)
—Tutoriels vidéo :YouTube, Udemy, Pluralsight
—Blogs techniques :Medium, Dev.to, blogs d’entreprises tech
